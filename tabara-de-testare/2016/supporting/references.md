# References

## Books

The programming books mentioned were:

* "Clean Code" by Robert Martin
    * A description of 'good' coding. Not my favourite book, I prefer any of the other 'programming' books mentioned in this section. But I prefer this to "Clean Coder" and I have read it twice so I do recommend it.
* "Growing Object-Oriented Software Guided by Tests"
    * An excellent book for showing how to use TDD, but also how to use 'usage' code to write abstractions, which is one way of creating abstraction layers for automating.
    * http://www.growing-object-oriented-software.com/
* "Working with legacy code" by Michael Feathers
    * Legacy code is essentially code without unit tests, which pretty much describes most of the code we write for "Test Automation". So when you have questions about how can we make our frameworks and abstractions maintainable? This book can help.
* "Implementation Patterns" by Kent Beck.
    * One of my favourite programming books. Encourages simplicity and making decisions. I continue to read this.
* "Domain Driven Design" by Eric Evans
    * A modern book about thinking about systems and architecture and their relationship to code. Can be hard going but is very worth reading.
* "Refactoring" by Martin Fowler
    * I tend to rely on 'right click, refactor' and pick one of the refactorings but it is useful to read this book and see how relatively small changes can shift your understanding of your underlying code to make it more readable and maintainable.

Older Programming Books. A lot of these are hard to get hold of, which is a massive shame. But if you can find any of them I recommend it.

* Glenford Myers - famous for writing "The Art of Software Testing" (which all testers have to read, but I don't really recommend) wrote several books which are very worthwhile reading:
    * Software Reliability
        * Very good at making the point that really we want to be "Software Developers" - not coders, or programmers, or testers, or architects - but people who can understand and work with the process of developing software.
    * Composite Structured Design
        * Explores different approaches to designing and architecting systems (what we might call abstraction layers) and the reasons and drawbacks for the different approaches. I found this a very useful book to go back to.
* Structured Programming by Dahl, DJkstra, Hoare - small essays that make up a body of knowledge from experience of writing code well.
* A Discipline of Programming by Djkstra - another great book on the practice of programming
* Essentially if you can pick up any of the older books by Djkstra, Yourdon, Tom de Marco you'll be better off.
* I like Michael Jackson's books particularly "Problem Frames" and "Software Requirements and Specifications" - they seem to have fallen by the way side now, but both of these (in fact all of Jackson's books) influenced how I approach the modeling of software.


This is a sampling of some great systems and cybernetics books. I recommend these, but you can start anywhere with any of these authors:

* Herbert Simon
    * Organizations - a great book on team dynamics
    * Research in Human Affairs - different ways of modeling the world
* Stafford Beer
    * Diagnosing the System for Organizations
    * Desiging Freedom
* W. Edwards Deming
    * Out of the Crisis
    * The new economics

Many of these books are actually about how teams work. But the same principles apply to our software systems as to our teams.

If you want to read about the history of automation then I recommend:

* John Deibold
    * Automation
    * Beyond Automation

And for classical Cybernetics: anything by Norbert Wiener or W. Ross Ashby
